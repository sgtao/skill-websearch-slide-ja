# write-md — スライドMD を書く規則（create / convert-raw で共通）

> 自分でスライドMD を書く・書き足すときに読む。ユーザーのスライドMD をそのまま変換するだけ
> （`workflows/convert-md.md`）のときは読まない。
> 前提: `workflows/build.md`「Step 2.5」で実効仕様を取得済みであること。

### type の選び分け（トラック別）

**この表は Step 3-0 をスキップした場合（テキストのみ・会話のみ）も使う。** 使う type は **Step 2.5 の実効仕様にあるものから選ぶ**
（下表に無い type も、実効仕様にあれば使ってよい。実効仕様に無い type は使わない）。

| 伝えたいもの | CLIトラック | レガシートラック |
|---|---|---|
| 手順・ワークフロー（人がたどる順番） | `steps`（優先） | `diagram-flow`／`points` |
| 抽象的な処理の流れ・階層・循環 | `diagram-flow` / `diagram-layer` / `diagram-cycle` | 同左（横フロー／縦レイヤー／サイクル） |
| 時系列・ロードマップ | `diagram-timeline` | `table`／`points` |
| 思い込み → 実際、の対比 | `contrast`（対比構造が明確なときだけ。多用しない） | 2カラム比較 |
| 工程表・体験の推移 | `svg-figure`（mermaid の `gantt` / `journey`） | `table` |
| 数量・構造・実物 | Step 3-0 の判定どおり（chart / diagram / figure） | 同左 |

新しい type を使うこと自体を目的にしない。文字で足りる内容は `points` のままにする
（`audience-purpose.md` の引き算方針を優先）。CLIトラックの type 名が上表と違う版では、
実効仕様の記載を優先する。

ビジュアル方針が「テキストのみ」のときは、図・グラフ・画像の type（`chart-*` / `diagram-*` /
`svg-figure` / `figure`）は使わない。`steps`・`contrast`・`table` は文字主体の type なので使ってよい。


### Step 4-A: スライドMD生成

Step 3 の構成スケルトンを `.md` に書き起こす。使用する仕様は Step 2.5 の結果で決まる。

- **CLIトラック かつ `--print-spec` 対応**: Step 2.5 で取得した `--print-spec` の出力（最新の
  スライドMD記法）にそのまま従う。`references/markdown-format.md` は使わない。
  初めて使う type の書き方に迷ったら、`--sample-md` をファイルに出力し、該当 type の
  スライドだけを検索して読む（全文は読まない。`cli-conversion.md` §3-3）
- **上記以外（CLIトラックで`--print-spec`非対応、または レガシートラック）**:
  `references/markdown-format.md` に従う。この仕様書はレガシートラックのLLM生成にも、
  CLIトラックの変換にもそのまま使える（chart-donut／comparison-chart／diagram-flowの記法が
  mdss-convertでもwarnings 0件・lint 0件で通ることを確認済み）
- frontmatter（`title` / `palette`）→ スライドディレクティブ（`<!-- slide: type -->`）→ 本文
- グラフは `chart` データ記述ブロック（推奨）、図解は `diagram` ブロックまたは `mermaid`
  サブセット（変換時にインラインSVG化。`mermaid.js` は最終HTMLに含めない）
- ファイル名: `{テーマ}-slides.md`

**共通記法の使いどころ（CLIトラックで実効仕様にあるときのみ）**

| 記法 | 使いどころ | 使わない場面 |
|---|---|---|
| `point:` | そのスライドの結論を1文で下部の帯に置く（ワンスライド・ワンメッセージ）。メインコンテンツのうち、結論を言い切れる枚だけ | 全スライドに機械的に付ける／本文の繰り返し／帯の中にインラインコード（バッククォート）を書く（mdss-convert v0.6.1 では文字が読めなくなる。コマンド名はそのまま書く） |
| `note:` | 数値の取得時点・根拠・話す順番など、スライドに書ききれない補足（スピーカーノート。スライドには出ない） | 出典URLの代わりにする（出典は chart の `source` と最終 `sources` に必ず書く） |
| `badge:` / `lead:` | 工程番号などの一言ラベル／見出しの補足1行 | 見出しと同じ内容の言い換え |
| `tone: dark` | デッキの中で最も強調したい 1〜2 枚だけ | 3枚以上、または連続するスライド |

**確認できない内容は書かない（要確認の明示・両トラック共通）**

本文に書く数値・固有名詞（製品名・社名・人名・版番号・日付）・実績や事例は、次のどちらかで
確認できたものだけにする。グラフの出典ルール（`chart-generation.md`）の本文版にあたる。

- Step 2 の Web 検索で得た出典に書かれている
- ユーザーが自分のデータ・事実として会話や添付で示した（出典スライドには `- [ユーザー提供](#)` と書く。
  mdss-convert v0.6.1 の `sources` は、リンクの形でない行を警告なしで表示しない）

どちらにも当たらないもの（自分の記憶にある値、会話に出たが出どころが分からない値、
出典を示さずに自分が以前の回答で述べた値）は、値を書かずに、その位置へ
`（要確認: ○○の最新値）` のように**何を確認すればよいか**を書く。

- 「約」「およそ」を付けて推測の値を書くことはしない（付けても確認済みにはならない）
- 要確認が増えて中身が薄く見えても、埋めるために推測を足さない。確認できた内容だけで
  構成し、足りなければ枚数を減らす
- 目的 C（SNS・顧客）の事例・実績・お客様の声は、確認できたもの以外は必ず要確認にする
  （`audience-purpose.md` の Verifier）
- 要確認にした箇所は、スライド番号・確認する内容・会話に出ていた値（あれば）を控えておき、
  Step 5 の完了報告に載せる。`point:` の帯とグラフのデータには要確認を置かない
  （結論が言い切れない枚には `point:` を付けない。グラフは Step 4-B の規則で `points` 等に置き換える）
- エントリポイント B / D（ユーザーが用意した MD・文章）の本文は書き換えない。構成のために
  **自分が足した**内容にだけこの規則を当てる
