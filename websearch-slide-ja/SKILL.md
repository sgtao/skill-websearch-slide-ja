# Slide Generator Skill with Web Search (Japanese)

ネット上の情報を調査・収集し、スライド形式のHTMLページを生成するスキル。

## 実行環境（最初に確認する）

このスキルは、ツール名や保存先を「選択式で確認する」「成果物を保存して提示する」のように
**操作の名前**で書いている。実際に使うツールとパス（Claude.ai / Claude Code / その他）は
`references/environment.md` の読み替え表に従う。**開始時に必ず読む。**

## ワークフロー概要

```
0.   スライド作成の確認（Yes / No）
1-A. 情報ソース確認（会話のみ / ハイブリッド / Web検索メイン）
1-B. テーマ・ロール確認
1-C. 検索フレーズ提案＋ビジュアル方針確認
2.   Web検索・情報収集
2.5. CLI環境診断＋実効仕様の取得（プリフライト）
3-0. ビジュアル化判定（グラフ / 図解）
3.   スライド構成の設計
4.   HTMLスライド生成（4-A: スライドMD → 4-B: HTML変換。エクスポート機能込み）
5.   ファイル出力・提示・検証
```

### エントリポイント判定（最初に必ず行う）

依頼と添付物から、以下のいずれかで開始する。

| 入力 | フロー |
|---|---|
| A) テーマの依頼（従来） | Step 0 → 1 → 2 → 2.5 → 3-0 → 3 → 4-A → 4-B → 5 |
| B) スライドMD添付＋「変換して」 | 簡易確認 → Step 2.5 → 4-B → 5（Step 1〜3 と検索はスキップ） |
| C) スライドHTML添付＋「MDにして」「編集して」 | Step 2.5 → 逆抽出（`--extract-md` またはmarkdown-format.md §7。`cli-conversion.md` §5参照）→ .md 提示 →（編集後）Step 4-B → 5 |
| D) 未準拠Markdown／CSV／会話履歴・プレーンテキスト | 入力タイプ判定 → Step 2.5 → 変換確認フロー → 4-B → 5 |

Step 2.5（CLI環境診断）はいずれの経路でも会話内で一度だけ実行し、以降 3-0・3・4-A・4-B・
逆抽出で結果を使い回す（詳細は `references/cli-conversion.md`）。
**A と D では MD を書く前（構成を決める前）に実行する**。使える type・枚数の目安・パレットは
CLI の版で変わるため、先に実効仕様を取得してから構成を決める。

B / C では `source-selection.md` のゲート群を通らず、Web検索も行わない。
スライドMD の仕様は `references/markdown-format.md` を参照。

### 入力タイプ判定

エントリポイント判定の直後、入力を以下の基準で自動分類する。

| タイプ | 判定条件 | 遷移先 |
|---|---|---|
| 完全スライドMD | frontmatter に `title:` があり、かつ `<!-- slide: ... -->` が1つ以上 | B) 直接 Step 4-B |
| 未準拠Markdown | Markdown 見出し(`#`)またはリスト(`-`)があるが上記を満たさない | D) 変換確認フローへ |
| CSV / TSV | 拡張子が `.csv`/`.tsv`、または明確な区切り表データ | D) 変換確認フローへ |
| 会話履歴／プレーンテキスト | 上記いずれでもない | D) 変換確認フローへ |

「frontmatter はあるが slide directive が無い」場合は**未準拠Markdown扱い**とする
（安全側の判定。誤って直接変換しない）。

### 変換確認フロー（エントリポイント D）

1. 入力を想定様式のスライドMDに変換する。
   - **1スライドの分量はユーザー指定がなければ「情報グループ優先」**で決める
     （見出し単位で自然に分割。Step 3 の枚数の目安には縛られない）
   - frontmatter の `title` は入力から推定、`palette` は未指定なら `ocean`
   - 箇条書き→`points`、表→`table`、数値データ→`chart` 等、内容に応じて type を
     割り当てる。使える type は Step 2.5 の実効仕様に従う（手順は、CLIトラックなら
     `steps`、レガシートラックなら `points`/`summary`。選び分けは Step 3 の表）
   - CSV の場合: 数値列があれば `chart` 候補として構造化する。出典は
     「ユーザー提供データ」である旨を明記し、`chart-generation.md` の
     数値・単位・出典ルールに準拠させる
2. **変換したスライドMDの全文をユーザーに提示**し、承認を得る
   （例: 「この構成でHTMLスライドを生成しますか？ 修正があれば指示してください」）
3. 承認 → Step 4-B（MD→HTML変換）→ Step 5（`.md` ＋ `.html` 両出力）
4. 修正指示があれば MD を修正して再提示する

## Step 0: 作成目的の確認

スキルが呼び出された時点で、**選択式の確認を逐次2回**行い、
「作成可否」→「作成目的」の順に確認する（1回の質問は2〜4択に収める。
使うツールは `references/environment.md`）。

### 0-1. 目的の推定（入力情報が多い場合・呼び出し1の前に実施）

会話履歴・長文テキスト・CSV 等、判断材料になる入力が既にある場合は、
呼び出し1の前に経緯を解析し、目的を推定する（`references/audience-purpose.md` 参照）。

| 手がかり | 推定される目的 |
|---|---|
| 「振り返り」「学んだこと」「メモ」「自分用」等の語 / 内省的な文体 | 自己学習・振り返り用 |
| 「チームに」「勉強会」「共有」「社内」「議論」等の語 / 業務文脈 | 社内共有・勉強会用 |
| 「発信」「投稿」「顧客」「提案」「訴求」「LP」等の語 / 説得・宣伝の文脈 | SNS発信・顧客プレゼン用 |
| 判断材料が乏しい | 推定しない（通常の順序で進める） |

推定できた場合は、後述の呼び出し2でその目的を選択肢の先頭に「（推奨）」付きで示す。
**推定はあくまで提案であり、必ずユーザーに確認を取る**（勝手に決めない）。

### 0-2. 呼び出し1（作成可否）

```
質問: HTMLベースのスライド資料を作成しますか？
選択肢:
  - 「はい、作成する」
  - 「いいえ、やめる」
```

- **「いいえ、やめる」** → 「了解しました。」と回答してスキルの処理を終了する
  （検索・生成は一切行わない）。呼び出し2は行わない
- **「はい、作成する」** → 呼び出し2 へ

### 0-3. 呼び出し2（作成目的・「はい」のときのみ）

```
質問: どんなスライド資料を作りますか？（目的に合わせて構成とトーンを最適化します）
選択肢:
  - 自己学習・振り返り用（思考を深める／教訓を残す）
  - 社内共有・勉強会用（チームに伝える／議論の土台にする）
  - SNS発信・顧客プレゼン用（相手の感情と行動を動かす）
  - まだ決めていない（おまかせ）
```

- 目的3種のいずれか → `references/audience-purpose.md` の該当トーンを適用して Step 1-A へ
- 「まだ決めていない（おまかせ）」→ 未選択フォールバック
  （`audience-purpose.md` の「目的が未選択・未確定のときのフォールバック」＝
  社内共有相当の中庸トーン）で Step 1-A へ

選択された目的は Step 3（構成設計）・Step 4（生成）・スタイル変更対話まで一貫して適用する。
スライドMD の frontmatter に `purpose:` として任意で記録してよい（`markdown-format.md` 参照）。

## Step 1-A: 情報ソース確認

`references/source-selection.md` を参照し、選択式で 3 択を提示する。

```
質問: スライド作成にどの情報を使いますか？
選択肢:
  - 「会話の内容だけでOK」
  - 「Web検索も追加する（会話 ＋ 検索）」
  - 「Web検索メインで（検索中心）」
```

### 「会話の内容だけでOK」選択時の下限チェック

`source-selection.md` の 4 観点（トピック数・具体性・分量・構造化可能性）をチェック。

- **不足なし**（2観点未満が該当）→ 通常モード（枚数は Step 3 の表）で Step 1-B へ
- **不足あり**（2観点以上が該当）→ 再確認の 3 択を提示：
  - 「Web検索で補う」→ ハイブリッドモード → Step 1-C へ
  - 「3枚でOK」→ 3 枚ミニモード確定 → Step 1-B へ
  - 「作成を中止する」→ 終了メッセージを出して処理を止める（検索・生成は一切行わない）

その他の選択時:
- 「Web検索も追加する」→ ハイブリッドモード → Step 1-B へ
- 「Web検索メインで」→ Web メインモード → Step 1-B へ

## Step 1-B: テーマ・ロール確認

会話履歴から **テーマ / 対象読者 / ユーザーロール** を抽出。不足分のみヒアリングする。
スライド枚数は選択モードに従う（3 枚ミニ、または通常モード。通常モードの枚数は Step 3 の表）。

**ロール推定の手順**

1. `references/role-signals.md` を読み込む（必ず実施）
2. 会話履歴のシグナルワードを照合し、2 個以上ヒットしたカテゴリを採用
3. 推定できた場合はヒアリングをスキップして Step 1-C へ
4. 推定できなかった場合は `role-signals.md` のヒアリング指針に従って確認

## Step 1-C: 検索フレーズ提案＋ビジュアル方針確認

> **スキップ条件**: Step 1-A で「会話のみ」かつ「3 枚でOK」確定時はスキップして Step 2.5 へ。

### 手順

1. `role-signals.md` の「参照ファイル」列で該当の `search-patterns/[カテゴリ].md` を読む（汎用なら `index.md`）
2. ロール × テーマで **デフォルト 3 個**の検索フレーズ候補を生成（広範テーマは最大 5 個まで）
3. ユーザーに提示し、修正・追加・削除を受け付ける

**提示例（テーマ「Claude Code」、ロール「エンジニア」）**

```
以下の検索フレーズで情報を集めようと思います。修正・追加はありますか？
1. claude code skill github stars
2. claude code tips tricks 2025
3. claude code 使い方 まとめ site:zenn.dev
```

4. 同時に、選択式でビジュアル方針を確認：

```
質問: スライドにグラフや画像を含めますか？
選択肢:
  - 「グラフ作成＋画像あり（Web 検索で取得）」
  - 「グラフ作成＋画像なし」
  - 「テキストのみでOK」
```

5. 確定したフレーズとビジュアル方針を記録して Step 2 へ

## Step 2: Web検索・情報収集

> **スキップ条件**: Step 1-A で「会話のみ」+ Step 1-C スキップ時は実行しない。会話履歴を構造化して Step 2.5 へ。
> **ハイブリッドモード**: 会話履歴を一次情報として先に構造化し、不足分のみ Web 検索で補完する。

### 検索クエリと回数

- Step 1-C で確定したフレーズをそのまま使う（**デフォルト 3 回**、最大 5 回）
- 職種別の追加クエリは `search-patterns/[カテゴリ].md` を参照
- 2024〜2026 年の情報を優先。GitHub スター数・X のいいね数を信頼性指標として活用

### 画像 URL の収集

ビジュアル方針が「グラフ作成＋画像あり」のときのみ実行。`references/image-embedding.md` を参照。

1. テーマ関連クエリで**画像検索を 1 回**だけ実行する（通常の Web 検索では画像 URL は取れない。
   画像検索の手段が無い環境では画像収集をスキップする。`references/environment.md` §3）
2. 返された URL を `image-embedding.md` の判断基準でフィルタ
3. 1 スライドにつき最大 1 件、結果を以下の形式で必ず出力（0 件でも「なし」と明記）：

```
[画像収集リスト]
スライド 3: 画像URL ... / 出典ページ ... / 説明「...」
スライド 4: なし（適切なURLが見つからなかったため）
```

### 数値データの抽出

ビジュアル方針が「テキストのみ」以外のとき実行。`chart-generation.md` の「データ抽出ルール」に従い、
**数値・単位・出典・取得時点が揃った候補のみ** を「[グラフデータ候補]」形式で記録する。
1 つでも欠ければ抽出しない（推測値の混入禁止）。

> 会話のみモード（3 枚ミニ含む）は原則スキップ。会話内に出典まで明示されている場合のみ例外的に許可。

## Step 2.5: CLI環境診断＋実効仕様の取得（プリフライト）

**構成を決める前に**、この会話内でまだ診断していなければ必ず実行する
（詳細は `references/cli-conversion.md` §2〜§3）。エントリポイント B / C では変換・逆抽出の直前に実行する。

このスキルは **CLIトラック**（`mdss-convert` に変換を委譲）と **レガシートラック**
（従来どおりLLMが直接HTMLを生成）の2経路を持つ。どちらになるかはこのステップで決まり、
以降の Step 3-0・3・4-A・4-B・5 の手順がトラックによって変わる。

1. `mdss-convert`（グローバル）または `npx -y mdss-convert@latest` が使えるか確認する
2. 使える場合、`--help` の出力から対応オプション（`--print-spec` / `--strict` /
   `--json-only` / `--extract-md` / `--guide-prompt` 等）と **`--palette` に並ぶパレットID** を確認する
3. **実効仕様を取得する**（CLIトラックのみ。会話内で各1回）
   - `--print-spec` 対応 → 実行して読む。**これが記法の正**（type 一覧・共通記法・`layout:`・制約・枚数の目安）
   - `--guide-prompt` 対応 → 実行して読む。**「type の選び分け指針」と「構成フレーム」だけを参考にする**。
     原稿作成をこのプロンプトに丸ごと任せない（目的確認・検索・出典管理は本スキルの役割）。
     記法の説明が `--print-spec` と食い違う箇所は `--print-spec` を正とする
   - `--print-spec` 非対応 → `references/markdown-format.md` を実効仕様とする
4. 判定結果（トラック・対応オプション・パレットID・実効仕様）は会話内で保持し、
   以降 Step 4-B を複数回実行しても再診断・再取得しない
5. 利用不可の場合は「今回はCLIが利用できないため、従来方式で作成します」と一言添え、
   以降はレガシートラック（[レガシー] 表記の手順）で進める。実効仕様は

## Step 4: スライド生成（MD中間層）

> 生成は「4-A: スライドMD生成 → 4-B: MD→HTML変換」の2段構成（CLI環境診断は Step 2.5 で済んでいる）。
> スライドMD が Single Source of Truth（正）であり、HTML は MD から毎回フル再生成する。
> エントリポイント B（MD添付）では Step 2.5 → 4-B の順で実行する（4-A はスキップ）。

トラック（CLI / レガシー）は Step 2.5 の診断結果で決まっており、経路によって Step 4-A・4-B の
具体的な手順が変わる。詳細な判定ロジックとコマンド組み立ては `references/cli-conversion.md` を参照。

### Step 4-A: スライドMD生成

Step 3 の構成スケルトンを `.md` に書き起こす。使用する仕様は Step 2.5 の結果で決まる。

- **CLIトラック かつ `--print-spec` 対応**: Step 2.5 で取得した `--print-spec` の出力（最新の
  スライドMD記法）にそのまま従う。`references/markdown-format.md` は使わない。
  初めて使う type の書き方に迷ったら、`--sample-md` をファイルに出力し、該当 type の
  スライドだけを検索して読む（全文は読まない。`cli-conversion.md` §3-3）
- **上記以外（CLIトラックで`--print-spec`非対応、または レガシートラック）**:
  `references/markdown-format.md` に従う。この仕様書はレガシートラックのLLM生成にも、
  CLIトラックの変換にもそのまま使える（chart-donut／comparison-chart／diagram-flowの記法が
  mdss-convertでもwarnings 0件・lint 0件で通ることを確認済み）
- frontmatter（`title` / `palette`）→ スライドディレクティブ（`<!-- slide: type -->`）→ 本文
- グラフは `chart` データ記述ブロック（推奨）、図解は `diagram` ブロックまたは `mermaid`
  サブセット（変換時にインラインSVG化。`mermaid.js` は最終HTMLに含めない）
- ファイル名: `{テーマ}-slides.md`

**共通記法の使いどころ（CLIトラックで実効仕様にあるときのみ）**

| 記法 | 使いどころ | 使わない場面 |
|---|---|---|
| `point:` | そのスライドの結論を1文で下部の帯に置く（ワンスライド・ワンメッセージ）。メインコンテンツのうち、結論を言い切れる枚だけ | 全スライドに機械的に付ける／本文の繰り返し／帯の中にインラインコード（バッククォート）を書く（mdss-convert v0.6.1 では文字が読めなくなる。コマンド名はそのまま書く） |
| `note:` | 数値の取得時点・根拠・話す順番など、スライドに書ききれない補足（スピーカーノート。スライドには出ない） | 出典URLの代わりにする（出典は chart の `source` と最終 `sources` に必ず書く） |
| `badge:` / `lead:` | 工程番号などの一言ラベル／見出しの補足1行 | 見出しと同じ内容の言い換え |
| `tone: dark` | デッキの中で最も強調したい 1〜2 枚だけ | 3枚以上、または連続するスライド |

**確認できない内容は書かない（要確認の明示・両トラック共通）**

本文に書く数値・固有名詞（製品名・社名・人名・版番号・日付）・実績や事例は、次のどちらかで
確認できたものだけにする。グラフの出典ルール（`chart-generation.md`）の本文版にあたる。

- Step 2 の Web 検索で得た出典に書かれている
- ユーザーが自分のデータ・事実として会話や添付で示した（出典スライドには「ユーザー提供」と書く）

どちらにも当たらないもの（自分の記憶にある値、会話に出たが出どころが分からない値、
出典を示さずに自分が以前の回答で述べた値）は、値を書かずに、その位置へ
`（要確認: ○○の最新値）` のように**何を確認すればよいか**を書く。

- 「約」「およそ」を付けて推測の値を書くことはしない（付けても確認済みにはならない）
- 要確認が増えて中身が薄く見えても、埋めるために推測を足さない。確認できた内容だけで
  構成し、足りなければ枚数を減らす
- 目的 C（SNS・顧客）の事例・実績・お客様の声は、確認できたもの以外は必ず要確認にする
  （`audience-purpose.md` の Verifier）
- 要確認にした箇所は、スライド番号・確認する内容・会話に出ていた値（あれば）を控えておき、
  Step 5 の完了報告に載せる。`point:` の帯とグラフのデータには要確認を置かない
  （結論が言い切れない枚には `point:` を付けない。グラフは Step 4-B の規則で `points` 等に置き換える）
- エントリポイント B / D（ユーザーが用意した MD・文章）の本文は書き換えない。構成のために
  **自分が足した**内容にだけこの規則を当てる

### Step 4-B: MD→HTML変換

```
CLIトラック:
  references/cli-conversion.md §4 のコマンド組み立てに従い、mdss-convert で変換する。
  変換結果（--json の warnings / lint）は必ず読み、次の「lintの扱い」で判定する。
  --strict が通った（exit 0）だけでは合格にしない

レガシートラック [レガシー]:
  以下の「生成手順」（本ステップ従来どおり）でLLMが直接HTMLを生成する
```

**lintの扱い（CLIトラック）**: `--strict` が止めるのは一部の error だけで、出典なしのグラフや
未知の type は warn のまま exit 0 になる（HTMLも出力される）。warn / error が1件でもあれば
内容を読み、下表に当てはめる（メッセージ文言の一致ではなく、内容で判断する）。

| lint / warnings の内容 | 扱い |
|---|---|
| `level: "error"`（`--strict` では exit 3・HTML未出力） | HTMLを提示しない。MDを直して再変換 |
| 出典が無い（chart / figure の `source`）・未知の type・最終スライドが `sources` でない（3枚ミニモードを除く） | **error と同じ扱い**。HTMLを提示せず、MDを直して再変換 |
| ブロックの形式不正（グラフ・図が描画されない）・切り捨て（系列数・ノード数・項目数の超過）・不正値のフォールバック | 内容が欠けるため、MDを直して再変換 |
| 上記以外の warn / info（例: 外部画像のCORS注意） | 再変換は不要。完了時に要約して伝える |

再変換は対象の warn / error が 0 件になるまで行う。
- **ユーザーが用意した MD・データ（エントリポイント B / D）で出典が無い場合**: 勝手に削らず、
  まず出典をユーザーに確認する。ユーザー自身のデータなら `source` に「ユーザー提供データ」と書く
- **出典が確認できないグラフ**（確認しても不明、または確認できない状況）: 数値を作らず、
  そのスライドを `points` 等のテキストに置き換え、置き換えたことを完了時に伝える
事前確認だけしたいときは `--json-only`（HTMLを出さずに lint だけ見る）を使ってよい。

frontmatter `palette` があれば `<html data-palette="...">` を焼き込み、
ドロップダウンの該当ボタンへ `is-active` を移す（`markdown-format.md` §6 / CLIトラックでは
mdss-convert側が同等の処理を行う）。

> 文言のトーン・強調・ネクストアクションは、Step 0 で確認した作成目的
> （`references/audience-purpose.md`）に従う。両トラック共通。

|------|------|------|-----------|

### 生成手順 [レガシートラックのみ]

**CLIトラックの場合は以下を一切行わない**（Step 4-BのCLIコマンド1回で完結する）。
レガシートラックの場合のみ、以下の手順でLLMが直接HTMLを組み立てる。

1. `assets/base-template.html` をコピーして土台にする
2. `assets/styles/` の **8 ファイル**を `<style>` に統合（`theme-vars → slide-core → nav-controls → figure → chart → diagram → list-view → print` の順、print.css は必ず最後）
3. `references/slide-layouts.md` を参照し、各スライドを `<section class="slide">` で記述
  - 10 行超のテーブル・20 項目超の一覧を含むスライドには `class="slide slide-fit"` を付与
4. **画像埋め込み**（ビジュアル方針「グラフ作成＋画像あり」のときのみ）
  - `references/image-embedding.md` の判断フローを実行
  - 1 件でも埋め込む場合、`assets/fallback-image.html` の `createFallback()` を `<script>` の先頭にコピー
  - 全 `<img>` に `onerror` でフォールバックを設定
  - HTML パターンは `image-embedding.md` を参照
5. **グラフ埋め込み**（Step 3-0 で採用されたときのみ）
  - 「[グラフ採用リスト]」の対象スライドに、採用テンプレートの SVG をコピー
  - プレースホルダー `{TITLE}` `{SOURCE}` データ値を実値に置換
  - `<div class="slide-chart">` でラップして配置
  - HTML パターンと座標計算は `chart-generation.md` を参照
  - 制約: SVG はインライン展開のみ。色は `chart-series-N` / `chart-line-N` クラス経由（ハードコード禁止）。外部グラフライブラリ禁止
6. **図解埋め込み**（Step 3-0 で図解採用のときのみ）
  - `references/diagram-generation.md` の座標テーブルに従い、`<svg class="diagram-svg" viewBox="0 0 960 480">` を `<div class="slide-diagram">` でラップして配置
  - パターン（横フロー / 縦レイヤー / サイクル）とノード数を選び、**既定座標にテキストを流し込む**（座標計算はしない）
  - 制約: SVG はインライン展開のみ。色は `diagram-*` クラス経由（`fill="#"` 禁止）。外部 `href` / `xlink:href` 禁止（完全自己完結）。長いラベルは `<tspan>` で手動 2 行に分割
  - グラフ・図解・画像は同一スライドに共存させない

### 5-A. ファイル出力

  - **CLIトラック**: 「`?` キーで操作一覧を表示できます」を基本に、主なキーだけ添える

    `V` 一覧切替 / `P` PDF / `Shift+S` PNG / `Shift+P` ZIP）

**完了報告（毎回・必須 7 項目）**

HTML を生成・再生成して提示するたびに、次の 7 項目を**各 1 行**で報告する（スタイル変更後の
再変換を含む）。項目は省略しない。該当が無い項目は「なし」、その経路で行わない項目は
「対象外」と書く。前置きやまとめの文は足さない。

| # | 項目 | 書く内容 |
|---|---|---|
| 1 | 生成物 | `.html` と `.md` の保存先パス、枚数 |
| 2 | トラック | CLI（版つき。例: `mdss-convert v0.6.1`）／レガシー |
| 3 | lint | error / warn / info の件数と、残った warn / info の要約。レガシートラックは「対象外（lint なし）」 |
| 4 | 要確認 | 件数と一覧（スライド番号: 確認する内容）。無ければ「なし」 |
| 5 | 情報ソース | 会話のみ／ハイブリッド／Web 検索、出典の件数。ユーザーの MD をそのまま変換したときは「ユーザー提供の MD」 |
| 6 | 未実施の検証 | 行っていない確認を具体的に書く（例: 見た目の目視確認／`validate-output.sh`／出典 URL が開けるかの確認） |
| 7 | 次にできること | `.md` を編集して「変換して」と送れば再生成できること。続けて操作の案内 |

- スライド番号は 1 始まり（表紙が 1）。lint の `slide` は 0 始まりなので 1 を足す
- 要確認が 3 件を超えるときだけ、4 の行に件数を書き、その下に 1 件 1 行で並べる。
  会話に出ていた値がある場合は「（会話では ○○）」と添える
- 6 は、実際に行ったことだけを検証済みとして扱う。変換が成功したこと・lint が 0 件であることは
  見た目の確認にはならない。行っていない確認を「問題ありません」と書かない
- 出典が確認できずテキストに置き換えたグラフ（Step 4-B）は、4 に含める

```
例（CLIトラック・会話のみ）:
1. 生成物: ./skill-improvement-slides.html / ./skill-improvement-slides.md（12 枚）
2. トラック: CLI（mdss-convert v0.6.1）
3. lint: error 0 / warn 0 / info 0
4. 要確認: 2 件（スライド 4: 導入社数の最新値（会話では 300 社）／スライド 9: 処理時間の短縮率）
5. 情報ソース: 会話のみ（出典 0 件）
6. 未実施の検証: 見た目の目視確認
7. 次にできること: .md を編集して「変換して」と送ると再生成できます。? キーで操作一覧を表示できます
```

### 5-B. 品質検証（Phase 5）

ユーザーが「品質を確認して」「検証して」「チェックして」と求めた場合、以下を実行する。
検証は**ユーザーの明示的な要求時のみ**実行する（デフォルトでは実行しない）。

**CLIトラックの場合**: `validate-output.sh` は対象外（レガシートラック向けのHTML実装
チェックのため）。代わりに Step 4-B の lint 判定（「lintの扱い」の表）が構造的な検証を兼ねている。
ユーザーには「CLI変換のためlintで検証済みです（warnings/lintの内容）」と結果を伝えて終了する。

**レガシートラックの場合**: `references/output-validation.md` を参照して以下のフローを実行する。

**検証フロー:**

1. `bash assets/scripts/validate-output.sh {出力ファイル}` を実行する
2. 結果を確認する：

**ALL PASS の場合:**
- 「検証完了: 全チェック項目を PASS しました。」とユーザーに報告して終了

**FAIL がある場合:**
- FAIL 項目をわかりやすく整理してユーザーに提示する（どのカテゴリで何が FAIL したか）
- 選択式で修正意思を確認する：

```
質問: チェック結果に問題がありました。修正しますか？
選択肢:
  - 「はい、修正する」
  - 「いいえ、このままでOK」
```

- **「はい、修正する」** → FAIL 箇所を修正して HTML を再生成し、再度 `validate-output.sh` を実行する。ALL PASS になるまで繰り返す
- **「いいえ、このままでOK」** → 「了解しました。」と回答する。ファイルが未提示なら提示し、提示済みなら回答のみで終了
